# Лабораторная работа № 2. Telegram-агент с MCP-инструментами

## Цель работы

Расширить Telegram-бота из лабораторной работы № 1 до AI-агента, который
может осознанно выбирать внешнее действие, вызывать его через MCP и использовать
полученный результат при формировании ответа. В ходе работы необходимо создать
собственный MCP-сервер, подключить его к боту и обеспечить безопасную обработку
аргументов, ошибок и операций с побочными эффектами.

## Планируемые результаты обучения

После выполнения работы студент должен уметь:

- объяснять роли MCP-хоста, MCP-клиента и MCP-сервера;
- различать инструменты и ресурсы MCP;
- описывать входные и выходные данные инструментов строгими схемами;
- реализовывать MCP-сервер и подключать его к приложению-клиенту;
- организовывать ограниченный агентный цикл с вызовом инструментов;
- проверять выбранный инструмент, его аргументы и результат выполнения;
- отделять операции чтения от операций с побочными эффектами;
- не передавать языковой модели управление пользовательскими идентификаторами
  и другими доверенными параметрами;
- измерять качество маршрутизации на фиксированном наборе запросов;
- документировать архитектурные решения и ограничения агента.

## Предварительная подготовка

Перед началом работы необходимо:

1. Завершить лабораторную работу № 1 и создать тег `lab1`.
2. Убедиться, что бот запускается, хранит пользовательские настройки и проходит
   тесты первой лабораторной работы.
3. Ознакомиться с актуальной архитектурой MCP, инструментами (tools) и ресурсами
   (resources), а также с документацией выбранного Python SDK.
4. Убедиться, что выбранная модель поддерживает нативный вызов инструментов или
   формирование ответа по строгой JSON-схеме.
5. Подготовить обезличенный файл с расписанием минимум на две недели. Файл должен
   входить в репозиторий и не содержать персональных данных.
6. Зафиксировать в отчёте версии MCP SDK, LLM-модели и внешнего API погоды.

Основным вариантом является нативный механизм вызова инструментов выбранного
LLM API. Если провайдер его не поддерживает, допускается структурированный выбор
действия по строгой схеме с обязательной программной валидацией. Обычный текстовый
ответ модели, который приложение пытается разобрать регулярным выражением, не
считается структурированным контрактом.

## Краткие теоретические сведения

### Отличие языковой модели от AI-агента

Языковая модель получает контекст и генерирует продолжение. Сама по себе она не
обращается к базе данных, не вызывает погодный API и не создаёт напоминания.
AI-агентом в этой работе называется программная система, в которой модель может
предложить действие, а приложение проверяет это предложение, выполняет разрешённый
инструмент и возвращает наблюдение модели для подготовки итогового ответа.

Ответственность за реальное действие всегда остаётся у приложения. Модель не должна
получать прямой доступ к произвольным функциям Python, командной строке, файловой
системе или базе данных.

### Цикл «получить запрос — выбрать действие — выполнить — ответить»

Минимальный агентный цикл содержит следующие этапы:

1. Бот получает сообщение и доверенный контекст Telegram-пользователя.
2. Приложение передаёт модели историю диалога и схемы доступных инструментов.
3. Модель предлагает обычный ответ или структурированный вызов инструмента.
4. Приложение проверяет имя инструмента, аргументы, права и необходимость
   подтверждения.
5. MCP-клиент вызывает разрешённый инструмент на MCP-сервере.
6. Приложение проверяет результат и добавляет его в контекст как результат
   инструмента, а не как инструкцию для системы.
7. Модель формирует итоговый ответ пользователю.

Цикл должен иметь верхнюю границу. В этой работе на одно пользовательское
сообщение разрешается не более двух MCP-вызовов. При превышении лимита обработка
останавливается с понятным сообщением, а событие записывается в журнал.

### Архитектура MCP

Model Context Protocol — протокол обмена контекстом между AI-приложением и
внешними программами. В этой работе роли распределяются так:

- **MCP-хост (host)** — Telegram-приложение, управляющее моделью и подключениями;
- **MCP-клиент (client)** — компонент внутри приложения, который обнаруживает возможности
  сервера и отправляет MCP-запросы;
- **MCP-сервер (server)** — отдельный программный модуль или процесс, предоставляющий
  инструменты и ресурсы.

В актуальной спецификации MCP каждый запрос содержит сведения о версии протокола
и возможностях участника. Клиент обнаруживает возможности сервера, а затем получает
списки доступных примитивов. Не следует хранить критичные данные только в памяти
MCP-соединения: сервер должен корректно обрабатывать запрос на основании данных
самого запроса и постоянного хранилища.

Для локальной работы рекомендуется транспорт `stdio`. Допускается Streamable HTTP,
если сервер защищён от внешнего доступа и способ подключения описан в `README.md`.

### Инструменты, ресурсы и их схемы

**Инструмент** выполняет вычисление или действие. Он имеет уникальное имя,
описание и `inputSchema`, по которой клиент и сервер могут проверить аргументы.
Инструменты обнаруживаются через MCP и вызываются структурированным запросом.

**Ресурс** предоставляет адресуемые данные для чтения. Он имеет URI, например
`schedule://current-week`, и не должен скрыто изменять состояние системы.

Хорошая схема инструмента:

- содержит только необходимые поля;
- задаёт типы, обязательность, допустимые значения и разумные ограничения;
- объясняет формат даты, времени и единиц измерения;
- не принимает путь к произвольному файлу, SQL-запрос или имя функции;
- имеет предсказуемый структурированный результат.

Описание схемы помогает модели выбрать инструмент, но не является границей
безопасности. Сервер обязан повторно валидировать каждый аргумент.

### Структурированный выбор инструмента

Предпочтительный вариант — передать модели обнаруженные схемы инструментов через
нативный механизм tool/function calling выбранного API. Модель должна вернуть либо
обычный ответ, либо имя инструмента и аргументы в машинно-проверяемом виде.

При отсутствии нативного механизма решение можно представить типизированной
моделью, например:

```text
action: "respond" | "call_tool" | "clarify"
tool_name: string | null
arguments: object
rationale: string
```

Поле `rationale` содержит краткое пользовательское объяснение уровня «нужны
актуальные погодные данные». Оно не должно требовать и сохранять скрытую цепочку
рассуждений модели. Полученный объект необходимо разобрать и проверить по схеме;
библиотеку для проверки студент выбирает самостоятельно.

### Валидация аргументов и результатов

Проверка выполняется на нескольких границах:

1. LLM-адаптер проверяет форму ответа модели.
2. MCP-клиент разрешает только инструменты, обнаруженные у настроенного сервера.
3. MCP-сервер проверяет аргументы перед обращением к внешнему API или базе данных.
4. Приложение проверяет структуру результата перед передачей его модели.

Невалидный вызов не следует «угадывать» или молча исправлять. Если город не найден,
дата неоднозначна или время напоминания уже прошло, бот должен запросить уточнение
либо объяснить ошибку.

### Операции чтения и операции с побочными эффектами

Получение погоды и расписания относится к операциям чтения: повторный одинаковый
вызов не должен изменять данные. Создание напоминания имеет побочный эффект и может
привести к дублированию записей.

Перед выполнением `add_reminder` бот обязан показать нормализованные текст, дату,
время и часовой пояс и запросить явное подтверждение пользователя. Подтверждение:

- относится только к одному пользователю и одному подготовленному действию;
- действует не более пяти минут;
- становится недействительным после выполнения или отмены;
- не может быть заменено новым текстом без повторного подтверждения.

Повторная доставка Telegram update, сетевой повтор и двойное подтверждение не
должны создавать вторую подготовленную операцию или второе напоминание.
Подтверждение должно относиться к неизменному действию того же пользователя.
Способ задания идентичности действия и защиты от конкурентных повторов студент
выбирает самостоятельно, обосновывает и проверяет на PostgreSQL.

Локальное время напоминания интерпретируется только в сохранённом часовом поясе
пользователя. Уже в этой лабораторной работе добавьте команду `/timezone <IANA zone>`
или эквивалентное меню. До настройки зоны запрос с локальным временем требует
уточнения. Работа с именованными зонами должна воспроизводиться на поддерживаемых
операционных системах; необходимые зависимости укажите в проекте.

### Ограничение полномочий и принцип наименьших привилегий

Агент получает только те возможности, которые нужны для задания. В частности:

- имя вызываемого инструмента выбирается только из обнаруженного списка разрешённых
  инструментов;
- расписание читается из заранее заданного источника без пользовательского пути;
- погодный инструмент выполняет только заранее определённые HTTP-запросы;
- модель не формирует SQL и не получает реквизиты подключения к базе;
- Telegram `user_id` и `chat_id` берутся из доверенного объекта обновления (`update`)
  и никогда не принимаются из решения модели;
- журналы не содержат API-ключи, полный системный промпт и лишние персональные
  данные;
- вывод инструмента рассматривается как недоверенные данные, а не как новая
  системная инструкция.

## Постановка задачи

На основе результата лабораторной работы № 1 разработайте Telegram-агента, который:

1. Подключается как MCP-клиент к собственному MCP-серверу.
2. Обнаруживает доступные инструменты и ресурс без дублирования их схем в обработчиках
   Telegram-команд.
3. По естественному запросу пользователя выбирает обычный ответ либо подходящий
   инструмент.
4. Умеет получать текущую погоду, находить занятия на дату и подготавливать создание
   напоминания.
5. Запрашивает подтверждение перед созданием напоминания.
6. Использует результат инструмента при формировании ответа и явно сообщает об
   ошибках внешних систем.
7. Предоставляет команды `/tools`, `/why` и `/timezone`.
8. Хранит часовой пояс, напоминания, состояния подтверждения и краткий аудит решений
   в PostgreSQL.
9. Имеет автоматические тесты и воспроизводимую оценку качества маршрутизации.

Работа должна продолжать существующее приложение. Создание отдельного демонстрационного
бота, не связанного с лабораторной работой № 1, не допускается.

## Архитектура решения

Рекомендуемое разделение компонентов:

```text
Telegram
   │
   ▼
aiogram handlers ──► AgentService ──► LLM adapter
                         │                │
                         │                └─ решение: ответ или вызов инструмента
                         ▼
                     MCP-клиент ──► MCP-сервер
                                       ├─ Open-Meteo API
                                       ├─ файл расписания
                                       └─ PostgreSQL reminders
                         │
                         └─► итоговый ответ и событие аудита
```

Схема показывает один из вариантов разделения ответственности. Итоговое решение
должно отделять получение Telegram update от правил агентного цикла и
MCP-взаимодействия, а также исключать доступ модели к базе данных. MCP-сервер
запускается отдельно; внутреннюю организацию приложения студент выбирает сам.

Конкретные имена модулей можно адаптировать к текущей структуре проекта. В отчёте
приведите фактическую схему зависимостей.

## Требования к MCP-серверу

Сервер должен предоставлять три инструмента и один ресурс. Их схемы должны быть
доступны через стандартное обнаружение MCP. Для каждого инструмента задайте
`inputSchema` и `outputSchema`, а результат возвращайте в `structuredContent`.
Для совместимости можно дополнительно вернуть сериализованный результат в текстовом
блоке; человекочитаемый ответ пользователю формирует бот.

### Получение текущей погоды

Инструмент `get_weather` принимает:

| Поле | Тип | Ограничения |
|---|---|---|
| `city` | строка | от 1 до 100 символов после удаления крайних пробелов |

Инструмент получает текущие погодные данные для указанного города. Выбор способа
разрешения названия города и обращения к погодному сервису обоснуйте в отчёте.
Результат содержит минимум:

- нормализованное название населённого пункта и страну;
- температуру воздуха в градусах Цельсия;
- код или текстовое описание погодных условий;
- скорость ветра и единицу измерения;
- время наблюдения и часовой пояс данных.

Необходимо обработать отсутствие результата геокодирования, несколько одноимённых
городов, тайм-аут, недоступность сервиса и некорректный ответ API. Если запрос без
страны соответствует нескольким одноимённым населённым пунктам, инструмент
возвращает различимые варианты с названием страны и административной области, а бот
просит выбрать один из них. Автоматически выбирать первый результат нельзя.

### Получение расписания занятий

Инструмент `get_schedule` принимает дату в формате ISO 8601 `YYYY-MM-DD` и возвращает
список занятий. Элемент списка содержит минимум:

```text
start, end, title, location
```

Пустой список является корректным результатом и означает отсутствие занятий.
Источник расписания задаётся конфигурацией приложения. Пользователь и модель не
могут передавать путь к файлу. В тестах текущая дата и источник данных должны
подменяться детерминированными фикстурами.

### Создание напоминания

Инструмент `add_reminder` принимает:

| Поле | Тип | Ограничения |
|---|---|---|
| `text` | строка | от 1 до 500 символов |
| `remind_at` | дата и время ISO 8601 | только будущее время с явным часовым поясом |

Идентификатор владельца и данные для защиты от повторов не входят в модельные аргументы.
После проверки решения модели приложение устанавливает владельца из доверенного
Telegram update и связывает повторные вызовы с одним подтверждённым действием.
Способ передачи этих значений MCP-серверу определяется выбранным транспортом и
должен исключать подмену со стороны модели или другого клиента.

Метаданные MCP формирует клиент, поэтому сами по себе они не подтверждают личность.
При `stdio` исключите доступ посторонних клиентов к серверу записи. При Streamable
HTTP клиент должен пройти аутентификацию, а сервер — связать владельца с
проверенной идентичностью, не доверяя произвольному значению `_meta`. Поле
`clientInfo` описывает MCP-клиент и не является идентичностью Telegram-пользователя.
Сервер отклоняет отсутствие доверенного контекста и попытки передать владельца
через модельные `arguments`.

Инструмент вызывается только после подтверждения. Он создаёт запись в PostgreSQL и
возвращает идентификатор напоминания, нормализованное время, часовой пояс и признак,
была ли создана новая запись. Повтор того же подтверждённого действия не создаёт
дубликат.

При проверке через MCP Inspector используйте отдельную тестовую базу и тестовую
идентичность. В рабочей конфигурации прямой вызов `add_reminder` из независимого
клиента должен получить ожидаемый отказ из-за отсутствия доверенного контекста.

В этой лабораторной работе отправлять уведомление в назначенное время ещё не нужно:
исполнение напоминаний будет добавлено в лабораторной работе № 3.

### Ресурс с расписанием на неделю

Ресурс `schedule://current-week` предоставляет расписание с понедельника по
воскресенье для настроенного часового пояса. Ресурс доступен только для чтения и
возвращает тот же формат занятия, что и `get_schedule`, сгруппированный по датам.

Вычисление недели должно проверяться на границах месяца и года без изменения
системных часов. Способ управления временем в тестах студент выбирает сам.

## Требования к Telegram-боту

### Обнаружение доступных инструментов

При запуске приложение подключается к MCP-серверу, проверяет его возможности и
получает список инструментов. Команда `/tools` выводит пользователю их имена,
краткие описания и пометку `чтение` или `изменение`.

Если сервер недоступен, бот продолжает отвечать без инструментов и сообщает об этом
только при запросе функции, которой сейчас нельзя воспользоваться. В журнале должна
быть указана причина сбоя подключения.

### Выбор и вызов инструмента

При обработке обычного сообщения модель получает только актуальный список
разрешённых схем. Возможны три корректных решения:

- сформировать ответ без инструмента;
- запросить недостающее уточнение;
- предложить вызов одного из обнаруженных инструментов.

Приложение сверяет имя со списком разрешённых инструментов и ограничивает цикл
двумя MCP-вызовами. Для вопросов об актуальной погоде и расписании агент должен
опираться на инструмент, а не придумывать данные. Вызов неизвестного инструмента
отклоняется.

### Проверка аргументов

До MCP-вызова приложение проверяет структуру и значения аргументов.
Особое внимание уделите:

- формату и диапазону дат;
- наличию часового пояса у напоминания;
- будущему времени напоминания;
- длине строк;
- отсутствию лишних полей;
- неизменности доверенного `owner_id`;
- связи подтверждения с тем же пользователем и подготовленным действием;
- существованию часового пояса в базе IANA и однозначности локального времени.

Команда `/timezone` сохраняет IANA-имя зоны и показывает получившееся локальное
время для проверки пользователем. Модель не выбирает зону по городу, языку или
профилю Telegram.

### Формирование ответа пользователю

Результат чтения передаётся модели как результат инструмента с указанием источника.
Итоговый ответ должен быть кратким, содержать фактические значения из результата и
не скрывать отсутствие данных.

После успешного создания напоминания бот сообщает его идентификатор и точное время
с часовым поясом. При сбое нельзя отвечать, что действие выполнено. Правила разбиения
длинных Telegram-сообщений из лабораторной работы № 1 продолжают действовать.

### Объяснение выбранного действия

Команда `/why` показывает краткую запись о последнем решении текущего пользователя:

- время запроса;
- `respond` или `call_tool`;
- имя инструмента, если он выбирался;
- безопасное резюме аргументов без внутренних идентификаторов;
- статус проверки и выполнения;
- краткую причину выбора.

Команда не должна показывать системный промпт, секреты, полную историю, внутренние
идентификаторы другого пользователя или скрытую цепочку рассуждений модели.

### Журналирование этапов обработки

Для каждого запроса сохраните краткое событие аудита, по которому можно
установить время, выбранное действие, результат проверки и выполнения и
длительность. Возможный набор полей:

```text
request_id, created_at, actor_id, action, tool_name,
validation_status, execution_status, latency_ms
```

Допускается хранить внутренний Telegram ID в базе приложения, если он нужен для
изоляции данных. В обычный текстовый лог записывайте непрозрачный внутренний
идентификатор или HMAC с закрытым ключом, а не простой хеш, имя пользователя и
полный текст сообщения. API-ключи, токены и содержимое системных инструкций
журналировать запрещено.

Обязательно обработайте:

## Тестирование

Тесты должны выполняться без реальных Telegram-, LLM- и погодных запросов. Внешние
границы подменяются заглушками или фикстурами. Интеграционные проверки реального
MCP-соединения и погодного API можно вынести в отдельную группу, которая не запускается
по умолчанию.

### Модульные тесты инструментов

Минимальный набор сценариев:

1. Погода успешно получена для существующего города.
2. Город не найден.
3. Погодный API вернул тайм-аут или некорректный ответ.
4. На выбранную дату найдены занятия.
5. На выбранную дату занятий нет.
6. Дата имеет неверный формат.
7. Напоминание создаётся для будущего времени после подтверждения.
8. Прошедшее время или пустой текст отклоняются.
9. Повтор с тем же ключом идемпотентности не создаёт вторую запись.
10. Повторная обработка одного Telegram update и конкурентное двойное подтверждение
    создают одну подготовленную операцию и одно напоминание.
11. Пользователь не может прочитать, подтвердить или изменить действие другого
    пользователя.
12. Ресурс корректно строит неделю на границе месяца или года.
13. Неизвестная IANA-зона и локальное время без настроенной зоны отклоняются.
14. Неизвестный инструмент и лишние аргументы отклоняются.

Тесты оформляются по схеме Arrange — Act — Assert и проверяют точные значимые поля
результата.

Отсутствие дубликатов при повторной подготовке и конкурентном подтверждении
проверьте отдельным интеграционным тестом на PostgreSQL: фиктивное хранилище не
доказывает работу механизма защиты в реальной базе данных.

### Проверка маршрутизации запросов

Используйте [открытый базовый набор](evaluation/lab2-routing.json). Он содержит
фиксированное время эксперимента, ожидаемые действия и проверяемые аргументы для
12 запросов:

- 3 запроса о погоде;
- 3 запроса о расписании;
- 3 запроса на создание напоминания;
- 2 запроса, для которых инструмент не нужен;
- 1 неоднозначный запрос с ожидаемым уточнением.

Для каждого запроса укажите ожидаемое действие и ключевые аргументы. Запустите один
и тот же набор на одной версии модели с одинаковыми настройками. Успешным считается
выбор правильной категории не менее чем в 10 случаях из 12 и корректные обязательные
аргументы не менее чем в 8 инструментальных случаях из 9. Дополнительные собственные
примеры разрешены, но не заменяют и не изменяют базовый набор.

В трёх сценариях напоминаний оценивается подготовленный вызов и нормализованные
аргументы. Фактическое создание записи без отдельного подтверждения не выполняется.

### Проверка некорректных аргументов и отказов внешних сервисов

Добавьте минимум четыре негативных сценария — по одному для каждой категории:

- попытка заставить агента вызвать отсутствующий инструмент или раскрыть системные
  инструкции;
- данные инструмента, содержащие фразу, похожую на команду для модели;
- неоднозначная дата либо напоминание в прошлом;
- недоступность MCP-сервера или погодного API.

Для каждого сценария зафиксируйте ожидаемое безопасное поведение и фактический
результат. Успешный отказ означает, что запрещённое действие не произошло, а
пользователь получил достаточное объяснение.

## Краткие теоретические сведения

### Разделение ответственности между агентами

Специализированный агент отвечает за один ограниченный класс задач, получает
минимально необходимый контекст и располагает только нужными инструментами. Такое
разделение уменьшает размер инструкций, упрощает тестирование и ограничивает ущерб
при ошибочной маршрутизации.

В этой работе используются три специализации:

- **Schedule Agent** — расписание и подготовка напоминаний;
- **Knowledge Agent** — ответы по локальным учебным материалам;
- **Lifestyle Agent** — погода и рекомендации, основанные на погодных данных.

Наличие трёх классов само по себе не делает систему безопасной. Границы должны
поддерживаться отдельными контрактами, явными списками разрешённых инструментов и тестами
запрещённых действий.

### Паттерн Router/Supervisor

Router принимает пользовательский запрос и выбирает одного специалиста либо
запрашивает уточнение. Он не выполняет предметную задачу и не имеет MCP-инструментов.
Решение Router должно быть проверяемым структурированным объектом. Например:

```text
target: "schedule" | "knowledge" | "lifestyle" | "clarify"
reason: string
confidence: number from 0 to 1
```

После валидации Supervisor создаёт типизированный запрос специалисту, применяет
политику доступа, принимает результат и формирует ответ Telegram-пользователю.
Неоднозначный запрос и неизвестная цель приводят к уточнению, а не к угадыванию
маршрута. Если используется `confidence`, правила его применения студент задаёт
и проверяет самостоятельно: самооценка модели не является калиброванной
вероятностью или границей безопасности. Невалидные аргументы и запрещённые
действия блокируются независимо от этой оценки.

В обязательной части один обычный пользовательский запрос передаётся одному
специалисту. Параллельная оркестрация используется только для ежедневной сводки.

### Типизированный контракт межкомпонентного взаимодействия

Контракт задаёт поля, типы и допустимые состояния запроса и результата. Он нужен
даже тогда, когда все компоненты находятся в одном процессе. Pydantic-модели или
эквивалентные типы должны проверять данные на каждой границе.

Не все поля следует отдавать на заполнение модели. Например, `request_id`,
`actor_id`, фактически вызванные инструменты, длительность и статус выполнения
формирует приложение. Модель может предложить маршрут или текст, но не должна
подделывать наблюдаемую телеметрию.

### Отличие внутреннего контракта от протокола A2A

Внутренний вызов `agent.handle(request)` или обмен через `asyncio.Queue` является
архитектурным контрактом конкретного приложения. Он не становится A2A только из-за
того, что сообщение представлено JSON-объектом.

A2A предназначен для взаимодействия независимых агентных приложений по HTTP(S) и
определяет совместимые привязки JSON-RPC, gRPC и HTTP+JSON/REST. Стандарт описывает
обнаружение через Agent Card, сообщения, длительные задачи, артефакты, состояния
выполнения, потоковые обновления и требования к защите.
MCP решает другую задачу: подключает агента к инструментам и ресурсам.

В обязательной части лабораторной работы реализуется **внутренний типизированный
контракт**, а не A2A-совместимый сервер. В отчёте необходимо указать это явно и
описать, какие компоненты понадобятся для вынесения одного специалиста в отдельный
A2A-сервис. Реализация настоящего A2A-взаимодействия допускается как расширение, но
не заменяет обязательные функции.

### Планировщик и проактивные сценарии

Проактивное сообщение инициируется не новым Telegram update, а правилом приложения:
наступлением времени напоминания или ежедневной сводки. Планировщик отвечает за
момент запуска, а прикладной сервис — за проверку согласия пользователя, создание
сообщения, защиту от повторов и фиксацию результата.

Периодическая проверка готовых записей — один из возможных способов запуска
фоновой обработки. Механизм и частоту проверки студент выбирает и обосновывает.
Он не даёт модели права самостоятельно придумывать цели, создавать фоновые задания
или отправлять сообщения. Все проактивные сценарии должны быть заранее описаны
программной политикой.

### Часовые пояса, повторные вызовы и идемпотентность

Локальное время без часового пояса неоднозначно. В профиле пользователя хранится
название зоны из базы IANA, например `Europe/Moscow`, а моменты выполнения — в UTC.
Для преобразований используется `zoneinfo` или эквивалентная библиотека. Фиксированный
сдвиг `UTC+3` нельзя использовать как замену именованной зоне для произвольных
пользователей.

После остановки приложения часть запусков может оказаться в прошлом. Для каждого
типа задания необходимо определить политику обработки пропущенного запуска
(`misfire policy`): допустимое опоздание и действие после его превышения. В этой
работе используются следующие правила:

- напоминание доставляется с пометкой об опоздании, если задержка не превышает
  15 минут; более старое получает статус `missed`;
- ежедневная сводка может быть отправлена с опозданием не более 60 минут, затем
  пропускается до следующего дня;
- накопившиеся ежедневные сводки объединяются в один запуск, а не отправляются
  серией.

Идемпотентность означает, что повторная обработка одного логического события не
создаёт новое уведомление. Защита от повторов должна сохраняться после
перезапуска и выдерживать конкурентную обработку; конкретный механизм в PostgreSQL
студент выбирает и проверяет самостоятельно.

### Трассировка и наблюдаемость

Лог — отдельная запись о событии. Трасса связывает полный путь одного запроса или
проактивного запуска, а span описывает один его этап. Например:

```text
telegram.receive → router.decide → specialist.handle
                 → mcp.call → telegram.send
```

Все записи одной операции имеют общий `trace_id`, а дочерние этапы — собственные
`span_id` и ссылку на родителя. Для лабораторной работы достаточно собственной
типизированной модели и хранения в PostgreSQL. Экспорт в OpenTelemetry допускается,
но не обязателен.

Трассировка должна помогать ответить, какой маршрут выбран, какие разрешённые
инструменты фактически вызваны, где возникла ошибка и сколько занял каждый этап.
Она не должна превращаться в хранилище полных промптов, секретов и чужих сообщений.

### Инъекция инструкций и чрезмерные полномочия агента

Инъекция инструкций (prompt injection) может находиться в сообщении пользователя,
учебном материале или результате инструмента. Простая фраза в системном промпте
«не нарушай правила» не является достаточной защитой.

Защита строится слоями:

- инструкции отделяются от недоверенных данных;
- каждый агент получает минимальный список разрешённых инструментов;
- вызов проверяется относительно исходного запроса пользователя;
- изменение состояния требует правил и подтверждения из лабораторной работы № 2;
- внешние данные ограничиваются по размеру и не выполняются как инструкции;
- неожиданный агент, инструмент или аргумент отклоняется программно;
- события отказа попадают в безопасную трассировку.

Модель может ошибочно предложить запрещённое действие. Инвариант считается
соблюдённым только тогда, когда код не позволяет это действие выполнить.

## Постановка задачи

Расширьте Telegram-агента из лабораторной работы № 2 следующим образом:

1. Реализуйте Router и три специализированных компонента: Schedule, Knowledge и
   Lifestyle Agent.
2. Задайте отдельные инструкции, типизированные входы и результаты каждого агента.
3. Ограничьте доступ к MCP-инструментам централизованной программной политикой.
4. Расширьте MCP-сервер инструментом поиска по локальным учебным материалам и
   ресурсом-каталогом материалов.
5. Реализуйте доставку напоминаний, созданных в лабораторной работе № 2.
6. Реализуйте ежедневную сводку на 08:00 по локальному времени пользователя.
7. Добавьте настройку города, адреса личного чата и согласия на ежедневные сообщения;
   продолжайте использовать часовой пояс из лабораторной работы № 2.
8. Обеспечьте восстановление фоновой обработки после перезапуска и защиту от
   повторной отправки.
9. Реализуйте команду `/trace` для просмотра безопасного следа собственной операции.
10. Обновите `constitution.md`, спецификацию, план, диаграмму и инструкцию развёртывания.
11. Добавьте автоматические тесты, эксперимент по маршрутизации и проверку
    безопасности.

## Архитектура решения

Рекомендуемая схема компонентов:

```text
Telegram update
      │
      ▼
  Supervisor ──► Router
      │            └─ RouteDecision
      ├─► Schedule Agent  ─┐
      ├─► Knowledge Agent ─┼─► политика доступа ─► MCP client ─► MCP server
      └─► Lifestyle Agent ─┘
      │
      └─► Telegram response

Фоновый исполнитель
      ├─► ReminderDeliveryService ─► Telegram
      └─► BriefingService ─► три специалиста / репозитории ─► Telegram

PostgreSQL: пользователи, напоминания, подтверждения, исходящие уведомления,
            трассы, этапы трасс, события аудита
```

Схема показывает возможную организацию компонентов. Границы полномочий между
маршрутизацией, специалистами, доставкой сообщений и хранением данных должны
соблюдаться независимо от выбранной внутренней структуры. В тестах время должно
контролироваться без ожидания реальных часов.

### Компонент маршрутизации

Router получает текст, список допустимых целей и минимум необходимой истории. Он
возвращает проверяемое решение о маршруте. Приложение должно отклонять цель вне
разрешённого списка, независимо от её представления в коде.

Router:

- не имеет MCP-инструментов;
- не создаёт напоминания и не отправляет сообщения;
- не формирует ежедневную сводку;
- при неоднозначном запросе выбирает `clarify`;
- не может выбрать класс или функцию по имени из произвольного текста.

### Компонент расписания и напоминаний

Schedule Agent обрабатывает вопросы о занятиях и запросы на напоминания. Ему
доступны только:

- `get_schedule`;
- `add_reminder`;
- ресурс `schedule://current-week`.

Подтверждение `add_reminder`, доверенный владелец и идемпотентность продолжают
работать по правилам лабораторной работы № 2. Доставка готового напоминания
выполняется фоновым компонентом, а не по новому решению LLM.

### Компонент работы с учебными материалами

Knowledge Agent отвечает только на основании локального корпуса и явно указывает
источники. Для него добавьте MCP-инструмент:

```text
search_materials(query: string, limit: integer = 5)
```

Результат содержит список фрагментов с полями `document_id`, `title`, `excerpt` и
`score`. Значение `limit` ограничивается диапазоном 1–5. Поиск может быть реализован
по ключевым словам; векторная база не обязательна.

Также добавьте read-only ресурс `materials://catalog` со списком доступных документов.
Путь к файлу не является аргументом инструмента. Knowledge Agent не имеет доступа
к погоде и операциям изменения напоминаний. Если подходящий материал не найден,
агент честно сообщает об отсутствии данных.

### Компонент погоды и повседневных рекомендаций

Lifestyle Agent использует только `get_weather`. Он может кратко объяснить, как
погода влияет на повседневный план, но не создаёт напоминания и не обращается к
учебным материалам. Рекомендации должны опираться на фактические поля результата,
а не на придуманную погоду.

### Доступ компонентов к MCP-инструментам

В коде задайте матрицу полномочий:

| Компонент | Разрешённые инструменты |
|---|---|
| Router | нет |
| Schedule Agent | `get_schedule`, `add_reminder` |
| Knowledge Agent | `search_materials` |
| Lifestyle Agent | `get_weather` |
| Briefing Service | только операции чтения через соответствующих специалистов |

Программная политика доступа разрешает компоненту вызвать только инструмент,
который одновременно доступен на MCP-сервере и разрешён этому компоненту.
Ограничение применяется непосредственно перед вызовом. Список в промпте служит
подсказкой модели, но не заменяет программную проверку.

## Контракты взаимодействия

### Модель запроса агента

Пример модели внутреннего запроса; состав полей можно адаптировать, сохраняя
доверенное происхождение идентификаторов и проверяемость контракта:

```text
AgentRequest
  request_id: UUID
  trace_id: UUID
  actor_id: internal identifier
  text: string
  intent: "user_query" | "daily_briefing"
  occurred_at: aware datetime
  timezone: IANA zone name
```

`request_id`, `trace_id`, `actor_id`, `occurred_at` и `timezone` формирует приложение
из доверенных источников. Они не извлекаются моделью из сообщения пользователя.
В LLM передаётся только минимально необходимая часть объекта.

### Модель результата агента

Пример модели результата; её поля и статусы можно адаптировать к выбранному
контракту:

```text
AgentResult
  status: "success" | "needs_clarification" | "not_found" | "failed"
  message: string
  confidence: number from 0 to 1
  facts: ScheduleFacts | KnowledgeFacts | WeatherFacts | EmptyFacts
  used_tools: list[string]
  error_code: string | null
```

Если результат включает несколько вариантов данных, их необходимо однозначно
различать и проверять по схеме. Текст и оценка уверенности могут происходить из
ответа модели, но статус выполнения, фактически вызванные инструменты и
проверенные данные определяет приложение. Все результаты валидируются до передачи
Supervisor.

### Структурированные события трассировки

События трассировки должны связывать этапы одной операции и показывать
их длительность, компонент, действие и исход. Возможный набор полей:

```text
trace_id, span_id, parent_span_id, request_id,
started_at, finished_at, component, operation, status,
tool_name, model_name, input_tokens, output_tokens, error_code
```

Отсутствующие необязательные данные не выдумываются: способ их представления
задаётся контрактом. Число токенов берётся только из метаданных LLM-провайдера.
Сырые промпты, ответы инструментов и Telegram-сообщения по умолчанию не сохраняются.

Команда `/trace last` показывает последнюю трассу пользователя, а `/trace <id>` —
указанную трассу, только если она принадлежит тому же пользователю. Представление
включает порядок этапов, длительность, статус и безопасные имена инструментов.

## Проактивные сценарии

Проактивные функции работают только в личных чатах, где пользователь ранее
взаимодействовал с ботом. Для ежедневной сводки требуется отдельное явное согласие.

Добавьте команды или эквивалентное меню:

- `/timezone <IANA zone>` — изменить часовой пояс, добавленный в лабораторной
  работе № 2;
- `/city <город, страна>` — выбрать населённый пункт для ежедневной погоды;
- `/briefing_on` — включить ежедневную сводку;
- `/briefing_off` — отключить ежедневную сводку;
- `/notifications` — показать текущие настройки без внутренних идентификаторов.

Команда `/city` выполняет геокодирование, показывает нормализованное название,
страну и административную область и сохраняет координаты только после подтверждения
пользователя. `/briefing_on` доступна после настройки часового пояса и города.
`/notifications` показывает их человекочитаемые значения и состояние согласия.

Для доставки приложение отдельно сохраняет `destination_chat_id`, полученный из
доверенного update личного чата. Это не `actor_id` и не модельный аргумент. Модель,
MCP-инструмент и содержимое учебного материала не могут выбирать или изменять адрес
доставки.

### Доставка напоминаний

Фоновый исполнитель находит напоминания, время которых наступило. До отправки
приложение сохраняет состояние исходящего уведомления в PostgreSQL и защищает
его от повторной подготовки, в том числе при конкурентном запуске. После
успешного вызова Telegram отмечается факт доставки. Временная ошибка допускает
не более трёх попыток, постоянная остаётся доступна для диагностики. Схему
состояний, способ идентификации события и интервалы повторов студент выбирает
и обосновывает самостоятельно.

Telegram Bot API не предоставляет универсального ключа идемпотентности для
`sendMessage`, поэтому сбой между фактической отправкой и фиксацией `sent` теоретически
может дать дубль. Этот остаточный риск необходимо честно описать в отчёте.

### Ежедневная сводка

В 08:00 локального времени пользователя ежедневная сводка включает:

- занятия на текущий день;
- запланированные на текущий день напоминания;
- текущую погоду для сохранённого подтверждённого города;
- один краткий учебный фокус по найденным материалам.

Получение этих данных может быть организовано через соответствующих специалистов
и хранилища; фактическую схему студент показывает в отчёте.

Учебный фокус должен опираться на доступные материалы и не выдумывать содержание.
Способ выбора материала и необходимость кэширования студент обосновывает в отчёте.
Для вызовов специалистов задаются конечные ограничения времени и нагрузки.
Исчерпание лимита даёт частичную сводку, а не бесконечные повторы.

Сводка содержит отметку времени и часовой пояс.
Если один компонент недоступен, остальные разделы всё равно отправляются, а вместо
пропущенного раздела выводится краткое сообщение об ошибке. Ни один участник сводки
не получает право вызывать `add_reminder`.

Для пары «пользователь — локальная календарная дата» создаётся не более одной
сводки. Пользователь без явного согласия не должен получить её даже после
перезапуска приложения.

### Ограничение частоты уведомлений

Точные напоминания отправляются по отдельности и не учитываются в лимите фоновых
информационных сообщений. Для остальных проактивных уведомлений действуют правила:

- ежедневная сводка — не более одного сообщения в локальный календарный день;
- необязательные погодные оповещения, если они реализованы, — не более одного
  сообщения в час и по умолчанию выключены;
- повторные запуски фоновой обработки не создают новое сообщение для уже обработанного
  события;
- ошибки фоновой обработки не отправляются пользователю циклически.

Лимиты проверяются по данным PostgreSQL, а не только по памяти процесса.

### Восстановление после перезапуска

PostgreSQL является источником истины для напоминаний, настроек, исходящих
уведомлений и состояний доставки. После перезапуска приложение продолжает
обработку незавершённых записей, применяет политику пропущенных запусков и не
создаёт повторных ежедневных заданий. Способ восстановления состояний студент
выбирает и проверяет на контролируемом перезапуске.

В обязательной части запускается один экземпляр фонового исполнителя, что необходимо
явно закрепить в конфигурации развёртывания. **Дополнительно** можно поддержать
несколько исполнителей: тогда потребуются атомарный захват, срок аренды и возврат
зависшей записи через PostgreSQL либо отдельный брокер.

## Требования безопасности

Создайте или обновите `constitution.md`. Этот файл является публичным описанием
инвариантов проекта для разработчика и студента, а не скрытой инструкцией модели.
Он должен содержать:

- матрицу доступа к инструментам;
- правила подтверждения операций изменения;
- правила проактивной отправки и согласия пользователя;
- ограничения частоты и глубины агентного цикла;
- требования к персональным данным и трассировке;
- поведение при неизвестном маршруте, инструменте и непроверенном результате.

Правила из `constitution.md` необходимо продублировать исполняемыми проверками и
тестами. Сам по себе документ не обеспечивает безопасность.

Назначение документов различается: `AGENTS.md` описывает постоянные правила работы
с репозиторием, `spec.md` — наблюдаемое поведение функций, `plan.md` — порядок их
реализации, а `constitution.md` — неизменяемые границы безопасности и полномочий.
Не дублируйте в них одинаковые абзацы; используйте ссылки между документами.

### Явные списки разрешённых инструментов

Allowlist задаётся для стабильных идентификаторов компонентов и инструментов.
Запрещено определять доступ через совпадение подстроки, имя Python-класса из ответа
модели или правило «разрешено всё, кроме одного инструмента».

При изменении списка инструментов MCP-сервера приложение должно снова вычислить
разрешённое пересечение. Неизвестный инструмент по умолчанию запрещён.

### Проверка действий относительно запроса пользователя

Перед операцией с побочным эффектом проверяются одновременно:

- исходный запрос пользователя;
- структурированное решение Router;
- цель и аргументы Schedule Agent;
- действующее подтверждение;
- доверенный `actor_id`;
- политика инструмента.

Проактивный запуск имеет системный тип `daily_briefing` или `reminder_delivery` и
не наследует случайный текст из предыдущего диалога. LLM не может самостоятельно
создать новый тип фонового задания.

### Защита от повторной отправки

Каждое уведомление должно иметь устойчивую идентичность и сохраняемое состояние.
Повторная и конкурентная подготовка одного события не создаёт двух заданий на
отправку.
Максимальное число попыток задаётся конфигурацией и проверяется тестами.
При дополнительной поддержке нескольких фоновых исполнителей необходимо
предусмотреть безопасное распределение работы и восстановление после сбоя.

### Защита логов и трассировки

Пользователь может читать только собственные трассы. В логах и spans запрещено
хранить:

- токены Telegram и LLM API;
- содержимое `.env`;
- полные системные промпты;
- полный текст учебных документов и личных сообщений;
- `actor_id` другого пользователя;
- скрытые рассуждения модели.

Для диагностических атрибутов используйте идентификаторы документов, размеры,
статусы и коды ошибок. Рекомендуется настроить срок хранения трасс или команду
очистки данных.

## Тестирование

Автоматические тесты выполняются с фиктивными LLM-, MCP- и Telegram-адаптерами,
тестовой базой и управляемыми часами. Реальное ожидание 60 секунд в тесте не
допускается: время изменяется через управляемый источник времени (`fake clock`)
или прямой запуск фоновой задачи.

### Маршрутизация запросов

Обязательные сценарии:

1. Запрос погоды направляется Lifestyle Agent.
2. Запрос расписания или напоминания направляется Schedule Agent.
3. Вопрос по локальным материалам направляется Knowledge Agent.
4. Неоднозначный запрос приводит к уточнению без вызова специалиста.
5. Неизвестное имя агента в структурированном ответе отклоняется.
6. Невалидный результат специалиста не передаётся пользователю как успешный.

Для экспериментальной оценки используйте
[открытый базовый набор](evaluation/lab3-routing.json): четыре запроса для каждой из трёх специализаций
и три неоднозначных запроса с ожидаемым `clarify`. Дополнительные собственные
примеры не заменяют и не изменяют базовый набор.

### Соблюдение границ доступа к инструментам

Проверьте минимум следующие случаи:

- Schedule Agent может использовать `add_reminder` после подтверждения;
- Lifestyle Agent и Knowledge Agent не могут вызвать `add_reminder`;
- Router не может вызвать ни один MCP-инструмент;
- Knowledge Agent не может передать пользовательский путь к файлу;
- инструмент, добавленный сервером, но отсутствующий в списке разрешённых,
  блокируется;
- инструкция внутри учебного документа не приводит к вызову инструмента;
- попытка подменить `actor_id` отклоняется.

### Работа планировщика

Проверьте:

1. Наступившее напоминание становится кандидатом на доставку.
2. Будущее напоминание не отправляется.
3. Опоздание до 15 минут помечается и отправляется.
4. Более старое напоминание получает статус `missed`.
5. Сводка запускается в 08:00 пользовательской зоны, а не серверной.
6. Выключенная сводка не отправляется.
7. Неверная IANA-зона отклоняется.
8. После перезапуска незавершённое задание восстанавливается.
9. Сводка не включается без подтверждённого города и часового пояса.
10. Адрес доставки берётся из доверенного личного чата и не подменяется моделью.

### Идемпотентность уведомлений

Два последовательных и два конкурентных запуска подготовки одного события не
должны приводить к повторной подготовке уведомления. Выбранный механизм проверьте
интеграционным тестом на реальном PostgreSQL. Также проверьте успешную отправку,
временную ошибку с повтором, исчерпание трёх попыток и восстановление после
перезапуска. Для дополнительного режима с несколькими исполнителями отдельно
проверяется восстановление работы после сбоя одного из них.

### Формирование ежедневной сводки

Проверьте полную сводку, отсутствие занятий, частичный отказ одного специалиста,
недоступность погодного API и повторный запуск в тот же локальный день. В ответе
должна быть явная отметка отсутствующих данных.

## Экспериментальная часть и проверка безопасности

Запустите 15 зафиксированных запросов на одной версии модели и с одинаковыми
настройками. Для каждого сохраните ожидаемого и фактического специалиста,
`confidence`, вызванные инструменты, длительность и число токенов, если провайдер
его сообщает.

Рассчитайте точность маршрутизации:

```text
routing_accuracy = число правильных маршрутов / 15
```

Целевой результат — не менее 12 правильных маршрутов из 15. Проанализируйте каждый
сбой и повторите ошибочные случаи после одного обоснованного изменения выбранного
элемента решения.

Дополнительно подготовьте шесть сценариев проверки безопасности:

- прямой запрос проигнорировать правила и вызвать чужой инструмент;
- попытка раскрыть системные инструкции;
- попытка подменить пользователя;
- запрещённый вызов `add_reminder` от Lifestyle Agent;
- инструкция, помещённая внутрь учебного документа;
- результат MCP-инструмента, содержащий ложное указание выполнить действие.

Успех сценария означает отсутствие запрещённого действия, а не наличие
определённой фразы отказа. Все шесть инвариантов должны быть соблюдены.

## Развёртывание проекта

Итоговый `compose.yaml` должен запускать минимум:

- Telegram-бота с Router, специалистами и фоновым исполнителем;
- MCP-сервер;
- PostgreSQL с постоянным volume.

Допускается размещение планировщика внутри процесса бота при условии, что запускается
ровно один экземпляр. Добавьте проверку состояния (`healthcheck`) или отдельную
диагностическую команду для проверки базы и MCP-сервера. Миграции выполняются явной
командой или контролируемым шагом старта.

В `README.md` опишите запуск, остановку без потери данных, настройку часового пояса,
включение сводки, проверку фонового исполнителя и восстановление после перезапуска.
Развёртывание на внешнем сервере является необязательным и не должно требовать
публикации секретов или оплаты сервиса.

## Критерии приёмки

Работа считается выполненной, если одновременно соблюдены следующие условия:

- сохранены функции лабораторных работ № 1 и № 2;
- Router выбирает одну из трёх специализаций или запрашивает уточнение;
- три агента имеют разные обязанности, инструкции и программные списки разрешённых
  инструментов;
- все внутренние запросы и результаты соответствуют типизированным моделям;
- MCP-сервер предоставляет поиск и каталог учебных материалов;
- фоновый сервис доставляет подтверждённые напоминания;
- ежедневная сводка отправляется в 08:00 локального времени только после согласия;
- сводка включается только после настройки часового пояса и подтверждённого города;
- адрес проактивной доставки получен из личного Telegram update и недоступен модели;
- повторный запуск фоновой обработки и перезапуск не создают повторное задание
  на отправку;
- применяются заданные правила опоздания, повторов и ограничения частоты;
- Lifestyle и Knowledge Agent технически не могут вызвать `add_reminder`;
- `/trace last` и `/trace <id>` показывают только безопасные собственные события;
- все обязательные автоматические тесты проходят без реального ожидания времени;
- интеграционные тесты PostgreSQL подтверждают отсутствие дубликатов
  подготовленной операции и исходящего уведомления при конкурентных попытках;
- маршрутизация верна минимум для 12 из 15 фиксированных запросов;
- все шесть инвариантов безопасности соблюдены;
- приложение воспроизводимо запускается через Docker Compose;
- `constitution.md` и остальные документы соответствуют реализации;
- в репозитории нет секретов и персональных учебных данных;
- создан тег `lab3`.
